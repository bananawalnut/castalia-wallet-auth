# Runtime provider profiles v1

Provider trust is explicitly approved runtime configuration. Fresh custody starts with zero profiles. No issuer, including Zenith, is required to build or operate Wallet. A compatible provider uses the same fixed signing contracts and capabilities as every other provider.

`getCapabilities()` reports implemented protocols independently of enrollment. `requestConnection()` approves an origin without enrolling or trusting an issuer. `proposeProviderProfile(profile)` proposes configuration and requires Wallet-owned consent; parsing and proposal submission never establish trust. Manual Wallet settings use the same parser. Browser proposals apply only to the requesting origin. Trusted manual import may cover several explicit origins.

The closed `castalia.provider-profile.v1` schema contains `display_name`, canonical `origins`, an optional `membership` purpose, and `presentations` pins. Every purpose is selected independently. Membership specifies a supported protocol, exact HTTPS issuer origin and Ed25519 roots. Presentation pins bind issuer, key, audience and exact callers. There are no arbitrary signing domains, adapters or executable configuration. Names convey no authority. The v3 membership protocol retains its historical `castalia.zenith-membership.v3` identifier and transcript bytes; that identifier does not restrict the issuer.

`listMembershipProfiles()` exposes active membership profiles scoped to an approved caller. `requestMembership({profileId})` joins only that selected profile after fresh consent. `getMembershipCredential({profileId})` re-verifies stored proofs against its current roots and holder. Proofs are keyed by profile, holder and credential digest, never just membership ID: v3 intentionally derives the same membership ID across issuers for one holder. Removing trust blocks use but retains proofs. Replacing identity clears the membership catalog and compatibility choices without erasing provider configuration. The old storage slot is preserved and can be read only after verification against an explicitly selected profile.

Legacy `getMembership` / `openMembershipFlow` require an explicit per-origin compatibility selection. There is no global default, first-profile fallback or auto-selection by display name. The new `requestRegistrationV2` is an additive transport entry point over unchanged typed manifest/consent/result bytes. It signs a proposal; it does not evaluate receiving-service enrollment eligibility. Legacy v1 retains its local membership check through the selected per-origin profile. Receiving services independently require signer-bound base-v3 membership for creation and accepted controller/revision state for updates. V4 community membership, profile approval and connection consent grant no operational authority.

The store is a bounded helper, not an authorization service. Its host must restrict writes to trusted UI, serialize configuration changes with custody final checks, invalidate preparations on revision/permission changes, and recheck the document, holder, epoch and expiry. Extension storage is restricted to `TRUSTED_CONTEXTS`; exact optional HTTPS host permission is requested from a user gesture. Enrollment omits cookies and rejects redirects. Inline custody uses its own explicit trusted UI and origin-local store; profiles do not synchronize browser data.

Existing Member Keys, recovery, authentication and Files signing bytes, registration manifests and Castaway formats are unchanged. Generic operation credentials remain transient; this catalog stores only existing membership credentials. Public profile metadata does not establish issuer ownership or receiver policy acceptance.

Bounds: 64 KiB per profile, 64 profiles, 64 origins, 64 roots/pins, 256 retained membership proofs. Unknown fields/versions/protocols, malformed origins, key ambiguity and capacity overflow fail closed. The checked-in fixture is synthetic configuration, never a default trust root.
